Contexto

Por qué existe este sistema

El requisito legal

ARBA exige el COT (Código de Operación de Traslado) para circular mercadería dentro de la Provincia de Buenos Aires. Cada remito debe obtener su código antes de salir.

La restricción

Existía un freeze sobre JDE: no se podían tocar objetos del ERP. Se construyó una solución por fuera, rápida, para no frenar la operación.

Hoy

JDE sigue sin tocarse. La solución provisoria quedó como sistema productivo crítico. Necesita modernizarse sin intervenir el ERP.

La propuesta de migrar el proceso dentro de JDE no es viable: la decisión es no desarrollar sobre el ERP. Por eso planteamos un sistema externo, moderno y web que replica lo actual y lo mejora.

Riesgo

Qué pasa si no se actúa

Riesgo de continuidad

Java Web Start está discontinuado. Una actualización de Windows o de Java puede dejar el sistema sin poder abrirse — y sin COT no sale mercadería.

Riesgo sobre los datos

Una base Access en red, sin backups y sin concurrencia, es un punto único de falla. Una corrupción del archivo no tiene recuperación garantizada.

Riesgo operativo

La integración por .exe y archivos depende de rutas y permisos del equipo. Si falla, el diagnóstico es manual y depende de una sola persona.

Riesgo de cumplimiento

Sin trazabilidad ni control de accesos, es difícil demostrar el correcto procesamiento de los traslados ante una auditoría.

Es deuda técnica que crece: cada mes que pasa, el sistema es más difícil y más caro de sostener.

La propuesta

Una plataforma web moderna que hace lo mismo — mejor

Replicar

El mismo modelo de datos, la misma lógica de negocio y la misma integración con el web service del COT. Cero sorpresas para el usuario.

Modernizar

Web, base centralizada multiusuario, seguridad, backups y trazabilidad. Accesible desde el navegador, sin instalar nada.

Sin tocar JDE

JDE sigue exportando sus CSV exactamente igual. El nuevo sistema los consume. Cero cambios en el ERP.

Principio rector: misma funcionalidad y misma operatoria conocida — la migración es de tecnología, no de proceso.

Migración Sistema COT · Coloplast10
Despliegue

Dónde se aloja el sistema — a definir con IT

Requisitos de conectividad — válidos para cualquier opción

① El backend necesita salida a internet hacia el web service de ARBA.    ② El servicio de ingesta necesita acceso a la carpeta CSV de la red interna de Coloplast.

Opción A · Servidor on-premise (Coloplast)

  • Acceso directo a la carpeta CSV y a la red interna
  • Los usuarios acceden por la LAN, sin exponer nada a internet
  • Datos dentro de Coloplast — favorable para cumplimiento
  • Solo hay que habilitar una salida puntual hacia ARBA
  • Requiere: 1 máquina virtual (Linux + Docker), recursos modestos

Opción B · Nube / hosting pago

  • No depende de hardware de Coloplast; despliegue rápido
  • ⚠ El server en la nube debe leer la carpeta CSV interna → VPN / túnel / agente
  • ⚠ Las restricciones de salida a internet pueden bloquear el acceso de los usuarios
  • ⚠ Costo mensual recurrente; datos fuera de la red corporativa

Recomendación: como los CSV viven en la red interna y suele haber restricción de salida a internet, un servidor on-premise es el camino de menor fricción. La nube es viable, pero primero hay que resolver la conectividad con la red interna.
